# Asterism 0.0.1 本地实施决策

> 仅保存在当前部署/开发克隆中，不提交、不推送。本文件整理自“从实际用的功能角度还缺什么”之后的产品讨论，是 0.0.1 后续实现与验收基线。若与旧 architecture、roadmap 或 research 文档冲突，以本文件和用户后续明确指令为准。

## 1. 发布口径与完成度

- 0.0.1 以“实际可部署、用户能完成平台任务”为标准，不以架构统一或语言统一为标准。
- 已验证上游具备且 Asterism 原样接入的能力，可以记为“可用（上游验证）”；不要求暑假期间必须找到新的未完成账号再次实测。
- Asterism 自研、没有上游或真实证据支撑的能力仍标记为“未验证”，直到夹具、只读账号验证或真实执行验证完成。
- 保留 WebUI、账号权限、课程/任务视图、题目与答案、Job/日志、Scheduler、多账号、API；Provider 实际执行优先调用上游薄 Worker。
- 外部题库第一版不实现。
- 新增 WELearn 课程在调试期间只读；正式发布不设置课程只读限制。
- 当前暑假真实账号验收允许在已结课且已完成、接近完成（约 90% 以上）的历史课程执行上游原有 mutation；
  进度为 0 的课程保持只读。任何真实写入都必须与题意相关，禁止自动化测试特征、无意义文本或无关内容。

## 2. 用户、QQ 与运行方式

- 普通用户账号可由管理员后台创建，也可由 QQ 创建；QQ 号作为账号标识。
- 管理员可以给用户挂课程和任务，适配不会操作 WebUI 的用户。
- QQ 使用 Yunzai v3 插件接入，并进入锅巴面板配置；不绑定某个精确 v3 小版本。
- 不依赖私聊：通知、确认均支持群内 @ 用户，附 WebUI 链接或确认命令。
- 课程添加时由用户或管理员配置自动巡检；默认关闭。关闭后仍可手动执行。
- 绑定 QQ 的账号可接收任务进度、失败、等待确认、截止未确认等通知。
- Provider 凭据、AI 站点和模型费用由平台管理员配置。

## 3. Provider 执行边界

### 3.1 Chaoxing

- 章节目录按官方知识点展示与勾选；支持批量全选，不把知识点内部的每个资源暴露为用户选择项。
- 作业与考试单独列出，不混入章节知识点目录。
- 章节任务点以完成/提交为目标，允许后台自动执行与自动提交，不要求逐题人工确认。
- 独立作业与独立考试自动获取题目、选答案并保存；最终提交必须人工确认。
- 有倒计时、进入即开始或有限次数的考试，在开始前也必须确认，不能为了扫描题目消耗一次机会。
- 页面没有显式保存按钮时，按平台原有退出自动保存行为处理并验证。
- 到截止时间仍未确认：绝不提交，必须通知用户。
- 复杂题与普通题一样支持批量选答案、填答和 Provider 原生提交，不因 Domain 不统一而默认退回人工。
- 需要覆盖：视频、章节测验、文档、阅读、累计阅读时长、直播真实时长、作业、考试、讨论、签到及上游已有的其他任务。
- 课程成绩构成页必须接入：模块占分比例、当前得分、完成条件、剩余缺口；覆盖视频、测验、作业、考试、阅读、直播、讨论等实际存在的模块。
- 阅读没有倍速；直播固定 1x，并通过平台重新获取的真实时长/状态验收。不得沿用上游“直播倍速后本地显示完成但平台未完成”的错误结果。

#### Chaoxing 并发与倍速

- 并发粒度是具体执行点，不是知识点。
- 管理员分别配置视频任务线程数、答题任务线程数、其他任务线程数。
- 不人为设置线程数上限；仅在上游证据或真实平台测试证明超过某阈值会失败时加入约束。
- 视频倍速默认 2x，不人为设置上限；平台或资源实际限制优先。
- 普通用户不接触线程数和倍速；管理员配置部署默认值，并可对单次执行覆盖。

#### Chaoxing 挑战模式

- 只调度当前已开放任务点；未开放节点不进入线程池，不反复尝试并刷错误日志。
- 当前开放节点完成后重新扫描，发现新解锁节点再继续。
- 因正确率不足无法解锁后续时，只重试阻塞解锁的答题任务。
- 首次普通作答后，普通策略最多重试 3 次；每次利用平台返回的判错、得分和历史失败答案调整答案。
- 仍未解锁时，使用 GPT-5.6 Sol、xhigh 思考等级最后尝试 1 次。
- 仍失败则终止该依赖链、记录明确错误并通知用户。
- 平台剩余次数或重做规则优先，不能假设存在更多机会。

#### Chaoxing 验证服务

- Chaoxing 的三类验证统一纳入 Asterism 的 Chaoxing Verification Service，所有
  Chaoxing Worker、历史扫描、课程知识点执行、Work 和 Exam 都通过同一个全局
  可调用边界请求验证，不在各调用点复制验证码逻辑。
- 第一类是 `upstreams/chaoxing`/CxKitty 提供的课程任务进度图片反爬验证码；
  第二类是 `upstreams/chaoxing-exam` 提供的 Exam 图片滑块验证码；第三类是
  `upstreams/chaoxing-exam` 提供的人脸/活体验证流程。三者都保留上游原始请求、
  Cookie 更新、Token/校验结果和原调用顺序。
- 三类验证都默认自动尝试，不转人工浏览器。每次验证使用有限次数和有限总时长；
  失败后指数退避、随机抖动并延后当前账号的扫描/执行，不能紧密循环重试或阻断
  其他账号。
- 验证重试按账号隔离：当前账号进入 `verification_backoff` 或
  `verification_failed`，保存课程、任务和分页游标；其他账号和 Provider 继续。
- 验证成功后刷新并持久化上游返回的会话材料，再从原游标/原执行阶段继续；不从头
  扫描，不重复提交已经确认成功的非幂等动作。
- 普通图片验证码优先复用 CxKitty 的 `ddddocr` 路径；Exam 滑块优先复用
  `chaoxing-exam` 的缺口计算和校验路径；人脸验证优先复用其已上传人脸/人脸比对
  路径。任何一类自动策略失败都只延后，不要求用户第一版值守拖动。
- 验证策略、最大尝试次数、总预算、退避上下限和最近结果在管理员后台可见，普通
  用户不需要看到底层验证码细节。

#### Chaoxing 富文本题干

- 题干、题组共享材料和每一个选项统一使用有序富内容结构；文字、下划线、挖空、公式、图片、音频、视频和文件附件允许任意混编并保留原始先后关系。不得退化为“纯文本 + 无位置附件列表”。
- 必须保留下划线和挖空语义，不能只保存 DOM 的纯文本。
- 有文字的 `<u>`、`text-decoration: underline`、下划线 class 等转成显式 `[UNDERLINE]...[/UNDERLINE]` 语义。
- `_` 字符、空 `<u>`、带下边框的空 span、NBSP/空格撑开的横线、input、textarea、可编辑区域统一识别为有序 `[BLANK_n]`。
- 多空题保留空位数量、顺序和平台字段绑定；提交依据 Provider 原始字段 ID，不依据横线长度猜测。
- 共享词框和共享材料进入题组上下文，并随每道子题传给题库/模型。
- 图片中的下划线或挖空保留为题干图片，交给视觉模型；题干图片和选项图片必须明确区分。
- 题库指纹包含下划线范围、空位、共享材料、共享词框、图片和 Provider 原生题型标记。
- 已从本地历史快照确认“大学英语2级”至少 31 道 `Replace the underlined part` 题在当前解析中丢失下划线范围，且共享词框没有进入 options；该问题必须作为回归夹具修复。
- 使用当前账号的“高等数学/高数”“有机化学”等历史课程进行只读样本采集，覆盖文本→图片→文本、内嵌公式、单个选项图文混排、多图选项、纯图片选项、共享材料混编和附件题；样本只读，不提交测试文本。

### 3.2 WELearn

- 按上游接口直接提交学习时长/正确率/完成状态，不为执行过程接 Asterism 通用题库。
- 题型本身不应阻塞完成；沿用上游已验证的直接完成和正确率路径。
- 并发对体验收益很小，遵循上游原有实现即可，不为它新建大型并发框架。
- 正式发布不保留调试期“两本新书只读”的限制。

### 3.3 UAI

- 沿用上游接口/浏览器逻辑直接完成必做章节，不为普通执行接通用题库。
- 单账号内串行；不同账号可以由 Asterism 调度器并行。
- 必做项目必须全部完成。讨论可用模型生成正常内容；Talk、口语、文件或其他特殊活动：不影响完成度则忽略，影响必做完成度则实现对应上游/浏览器路径。
- UAI 平台行为较脆弱，不主动提高单账号并发。
- UAI 讨论必须先通过 Worker 新鲜读取远端题目/上下文，AI 只返回有边界的正常人类纯文本，再由 Worker 按 donor 原顺序发布；生成内容作为加密、不可变、任务绑定的调用草稿保存。WebUI 允许在执行前预览、修改并重新准备。
- AI 讨论草稿可选择“默认省钱组合”或“GPT-only 保质组合”；生成草稿本身绝不等于执行或提交。
- 不接入 UAI 上游自带的 AI/答案链作为 Asterism 的默认答案来源。UAI 仅使用其已验证的
  完成率、必做章节、讨论/特殊活动和驻留时长执行逻辑；需要答案时走 Asterism 自己的
  Provider Native/全局题库/AI 选择链。

### 3.4 Cidaren

- 后端来源合并后的纯后端仓库作为 donor；Asterism 中保留调用与 WebUI，不使用 donor UI。
- 登录只保留后来研究的微信授权流程：WebUI 展示二维码或授权链接，用户在微信验证后把最终跳转链接复制回 WebUI。无需 MITM/抓包登录。
- 单账号内严格串行，因为下一题通常依赖上一题提交返回的 topic_code；不同账号可并行。
- 目标是尽可能提高正确率，而不接受上游随机猜题作为正常答案策略。
- 平台/历史 `answer_lib` 作为 Provider 分区的全局题库证据接入，不建立另一套孤立答案库。
- 限时题优先等待配置的 Instant 模型；确定性推导也必须先等 Instant，不直接信任本地推导。
- 时间预算默认：前 65% 等模型，65% 后启动本地兜底，85% 使用当前最佳答案，最后 15% 留给提交和一次网络重试。
- 若模型仍未返回：使用可信度最高的推断；实在无法判断则选择一个答案以保证完成。
- 限时题延时必须限制在安全时间预算内，呈现正常作答频率；非限时任务的延时可在提交任务时配置。
- 将上游 `answer_lib`、历史题库和可解析的答案记录导入部署内全局题库，标记为
  `ProviderNative`/历史观测来源，但固定为低可信度历史证据，不得当作平台标准答案直接提交；
  `answer_lib` 本身只有词/短语到答案的映射，无法安全生成完整 Question 身份，因此采用“新鲜题目
  读取后按完整题意绑定、命中即懒导入”的方式；不把无法绑定题干、材料和规范化选项的原始词表伪造为题库题目。
  导入不按题号、选项 ID 或展示顺序匹配，只按完整题意、材料和规范化选项内容建立题库身份。
  导入记录不覆盖已有正确/错误观测，冲突按全局题库规则进入模型仲裁。

## 4. 部署内全局题库

- 现有“同一 owner、同一 task 的 Local Cache”机制废弃，改为当前部署环境内全局共享。
- 题库首先按 Provider 分区；WELearn、UAI 不进入通用选答案执行链。不同 Provider 不因题干相同直接共享答案。
- QuestionSnapshot 继续不可变；题库保存题目身份、答案变体和每次观测，而不是只留一个最终值。
- 所有答案都缓存：Provider 返回、历史作答、人工补漏、AI 输出、正确、错误、未验证。
- AI 返回后立即以“未验证”保存；平台验收后追加正确或错误观测。
- Provider 当前任务直接返回的标准答案优先级最高，可直接使用且不经过模型。
- 已验证精确缓存：某答案变体已有至少一次正确记录，并且当前所有有结论的观测均为正确时，经济组合可以直接复用。
- 同一答案既有正确又有错误记录时进入模型仲裁，不删除任一历史记录；教师可能配置错误答案，不能一次判错永久封杀。
- 多个不同答案都存在正向记录时进入模型仲裁。
- 只有错误记录的答案作为负面证据，不作为候选提交。
- 若能识别课程、教师、班级、作业版本等上下文，则保留上下文分支；上下文分支内全部正确时可直接复用，不覆盖部署全局冲突事实。
- 删除“Private Evidence”作为产品层级；来源、课程、任务、教师、时间、判定等仍作为普通观测元数据保存。
- 不限制为简单题或纯文本题。Matching、Ordering、Composite、共享选项、完形、阅读、图片、附件、Provider-native 等均进入题库。
- 题库身份包含 Provider、完整题组祖先、题干结构、选项内容、题干图片、选项图片、附件、共享材料、空位/下划线和 Provider 原生题型标记；题号、题目/题组远端 ID、位置、选项 ID 和展示顺序不参与题库身份。图片/附件优先以内容摘要识别，没有摘要时才保守使用稳定的无凭据远端引用。
- 选择类答案按规范化后的选项内容（含选项图片语义）保存和匹配，不把 `A/B/C`、远端数字 ID、展示顺序或题号当成题库身份；复用时再将唯一内容重绑定到当前题目的 Provider 选项 ID。内容重复或映射不唯一时禁止直接命中，转入模型或提交前补漏。
- 图片选项先按去除签名/临时查询参数后的稳定 URL 或资源标识及其哈希匹配；不一致时尝试内容摘要，仍无法唯一匹配时交给视觉模型，禁止按原位置猜测。
- 对四个平台执行一次“语义身份/提交绑定分离”审计：题号、题目顺序、题组/题目远端 ID、选项字母/数字 ID、空位控件 ID、短期图片 URL、课程/任务旧类型影子记录都只能作为当前快照与提交路由；题库复用只依赖完整题意材料。为随机选项顺序、随机题序、远端 ID 变化、签名 URL 变化和重复选项补回归测试。
- 客观题答案可部署内全局直接复用；主观答案也保存为全局参考证据，但不同用户提交时必须重新生成差异化文本。同一用户自己的历史答案可在上下文一致时复用。
- 人工环节称为“提交前确认和补漏”，不作为答案来源顺序中的一个自动步骤。

## 5. 答案选择顺序

1. Provider Native：平台当前任务直接给出的标准答案或确定性完成接口。
2. 部署内全局精确缓存。
3. 可选廉价模型验证。
4. 外部题库与 AI：第一版外部题库关闭，因此当前走 AI。
5. 客观题多来源答案一致则采用；不一致走模型仲裁。
6. 主观题优先走模型，输出正常人类 plain text。

- 平台直接给出的标准答案不经过模型。
- GPT-only 模式中，已验证精确缓存只作为证据，仍需模型检查；平台当前返回的标准答案仍直接使用。
- 不限时题配置一个主模型即可，不做无意义的多模型同时请求。
- AI、平台、人工、历史答案都进入同一缓存闭环。

## 6. AI 端点与组合

- GPT Router 地址暂时留空，由管理员部署时填写。
- GPT Router 使用 Responses API；内部定义中立的 AiRequest/AiAnswer，Provider 适配器负责 Responses 或兼容接口映射。
- 远端请求 `store: false`；这只禁止模型站保存请求，不影响 Asterism 本地答案缓存。
- 支持多个站点、多个模型、不同思考等级和按任务类型选择模型。
- 管理员可以保存执行组合，并在单次任务执行时覆盖组合、模型与思考等级。
- 管理员可设置部署默认组合；课程自动巡检可单独覆盖为 `economy` 或 `gpt_only`，显式清除后继承部署默认，
  且生成讨论草稿与实际 Execution 使用同一冻结组合。

### 经济组合（默认）

- Provider 标准答案/直接完成：直接使用，不调用 AI。
- 已验证精确缓存：直接使用；可配置廉价模型验证。
- 限时未知题：GPT Router 的 GPT-5.6 Luna，low。
- 不限时未知题：GPT Router 的 GPT-5.6 Terra，medium。
- 难题、冲突、格式异常、挑战模式最终升级：GPT-5.6 Sol，high/xhigh；挑战模式最终一次固定 xhigh。
- GPT Router 请求失败、超时或不可用时才启用国内灾备：受约束客观文本使用 DeepSeek；主观、多模态、文件富内容使用 Kimi。
- 不默认使用豆包。

### GPT-only 高质量组合

- Provider 标准答案/直接完成：直接使用，不调用 AI。
- 已验证精确缓存：作为证据交给模型复核。
- 限时题：GPT-5.6 Luna。
- 不限时题：GPT-5.6 Sol，xhigh。
- 不使用国内灾备。

### 模型输入与输出

- 平台提供的全部题目上下文均传入：题干、题干图片、选项、选项图片、共享材料、附件、题型、空位、下划线、历史正确/错误证据。
- 题干图片与选项图片明确标记，不能混成无归属图片列表。
- 主观题输出严格限制为正常人类 plain text，不包含 Markdown 包装、系统解释、JSON 痕迹、自动化测试文本或无关内容。
- 多人同题执行时进行措辞差异化，并自动检查引用、格式和重复内容。

## 7. 提交与人工确认

- 课程章节任务：以完成为优先，可自动提交，不需要逐次授权。
- 独立作业、考试及其他独立高风险任务：自动填答/保存，最终提交必须人工确认。
- 有倒计时或进入即消耗机会的考试：开始前确认，交卷前再次确认。
- 提交前确认可通过 WebUI 或 QQ 群 @ 通知完成。
- QQ 群确认链接使用 10 分钟、单次消费、绑定安全相对跳转路径的网页登录票据；打开后建立正常 HttpOnly Web Session。不得把 `ast_ws` API bearer 放入 URL。
- 截止仍未确认：保持草稿/已保存状态，绝不自动提交，通知用户和必要时通知管理员。
- 计分讨论默认生成符合题意的差异化内容；是否直接发布跟随课程任务策略。只有确实影响完成度/成绩的回复、点赞等交互才执行。

## 8. Scheduler、巡检与日志

- Scheduler 只决定何时运行、账号、课程/任务、Job 状态、日志与结果；Provider Worker 决定内部执行细节。
- 批量任务允许简单创建多个 Worker Job，不以通用 parent/child BatchExecution 为发布前置条件。
- 自动巡检默认关闭；启用后只处理用户/管理员选择的课程与策略。
- 平台账号拥有者可以配置自己账号的巡查计划；管理员仍可跨用户配置。Provider 全局运行设置与
  Chaoxing 全账号历史题库扫描控制继续仅对管理员开放，避免把部署级策略误暴露给普通用户。
- 课程级自动执行复用既有 `automation_plans`，不新建终态 SDK/状态机。每次账号巡查成功后只遍历显式启用的课程，
  自动调度已开放、未完成、非正式且可直接执行的任务；Chaoxing 只自动调度章节知识点，UAI 只自动调度平台明确标为
  必做的章节和讨论任务；讨论先生成严格 plain-text 草稿再走 Worker 原生发布边界。正式作业/考试和需要提交前确认
  的任务永不被这条后台路径自动提交。
- Job 日志必须区分：等待开放、等待模型、等待用户确认、平台次数不足、正确率不足、解锁失败、网络失败、Provider 协议变化。
- 已完成课程仍允许只读扫描、题型采集和历史正确答案回收；不得写入明显测试文本或无意义内容。

### Chaoxing 全账号静默扫描
