# Asterism 0.0.1 全仓审计与 Windows 安装向导规划

> 状态：规划与审计基线。本文档本轮只记录范围、语义、验收标准和实施顺序，不代表下列缺口已经修复。
>
> 目标：在不扩大 Provider 重写范围的前提下，把现有 WebUI、统一题库、调度、Job/日志/状态和四个上游 Worker 收口为可部署产品；首个安装目标为 Windows Server/Windows 10/11，反向代理不由安装向导处理。

实现进度以提交和测试为准；当前已落地 QQ master assertion、Web/Yunzai target-owner 上下文、Windows 安装器及其无人值守密码文件入口。GitHub Actions Windows smoke 已在 `32944360652` 通过（中文/空格路径、venv、daemon、Master bootstrap、Yunzai token、validate）；四 Provider 的真实账号现场验证、用户自有 Windows Server 安装回归和全部逐路由代用户验收仍不能仅凭代码测试宣称完成。

## 1. 总原则

1. Asterism 是控制面；实际平台协议、登录、页面操作、提交和特殊题型优先复用已审计 upstream。
2. 所有权与操作者分离：`owner_user_id` 表示资源、任务、余额和通知归属；`actor_user_id` 表示实际发起操作的用户或管理员。任何管理员代执行都必须同时记录两者。
3. QQ 机器人是注册入口，不是新的用户类型。普通用户和管理员都对应同一套 Asterism 用户；Yunzai 事件中的 `e.isMaster` 只能由受信任的插件侧产生，并映射为 master 操作身份。
4. 本地部署数据、密钥、题库和日志不上传云端。安装器不得把凭据写入命令行、普通日志或前端源码。
5. 只读验证、扫描和静默后台扫描是检查点，不得误报为全部功能已完成；每个能力必须有代码、证据和可执行验收。

## 2. 全仓审计矩阵

审计结果使用：`已实现`、`部分实现`、`待补全`、`现场未验证`。实现阶段每一行都要补上测试或现场验证记录。

### 2.1 身份、登录与权限

### 2.2 管理员代用户与所有权边界

这是当前最高优先级的语义审计项。现在 WebUI 可以在创建 Provider Account 时填写 `owner_user_id`，但后续许多 account/course/task/execution 路由仍以当前 principal 作为 owner；因此“创建给别人”与“继续操作别人资源”尚未形成完整闭环，不能宣称已完成。

必须统一审计并补齐以下对象：

- Provider Account、凭据、认证会话、重新认证、健康检查和扫描。
- Course、Task、章节/知识点、题目快照、答案候选、答案历史和题库命中。
- Job、Execution、日志、事件流、取消、重试、批量任务和调度计划。
- BrowserBridge/Capture、运行时设置、AI 配置/用量、Cidaren bridge、通知目标和余额扣费。

目标 API 语义：请求显式携带 `target_owner_user_id`（普通用户只能是自己）；服务端同时记录 `actor_user_id`、`owner_user_id`、权限来源和审计原因。管理员在 WebUI/QQ 执行时先选择目标用户，再选择账号/课程/任务；用户看到的进度、确认链接、通知和扣点都归目标用户。管理员不因代操作而把自己的余额或通知目标混入任务。

### 2.3 Provider 能力闭环

#### Chaoxing

按 upstream 能力逐项审计：登录、Cookie/JWT、课程与章节目录、知识点、视频/阅读/直播/讨论、作业、考试型任务、部分提交、进度与成绩构成、题目扫描、全局题库、混编题干/选项图片、附件/共享材料、填空下划线、连线/共用选项/复合题、挑战模式、三类验证码、倍速与并发、失败延后重试、截止时间冻结、人工提交前确认。

要求：

- 知识点按官方目录展示，作业和考试独立列出；批量勾选按执行点而非把知识点内部题目拆成 UI 项。
- 视频/答题/其他执行点分别配置并发；直播默认 1x，普通视频默认 2x；不对配置人为设上限，但对已知平台限制做运行时保护。
- 挑战模式只处理已开放节点；失败重试 3 次，再用 Sol xhigh 1 次，仍失败才报错。
- 三类验证码都进入统一 Chaoxing 验证策略：自动尝试、失败延后重试并记录原因；不默认转人工。需保留可观测的阻断状态，避免一个账号阻断全局扫描。
- 课程内任务可按策略自动提交；独立作业/考试必须人工确认。到截止时间仍未确认时绝不提交，只通知用户。

#### WELearn

复用 upstream 的完成率和时长接口/执行顺序。完成与时长保持可分离的阶段，不能为了统一 Core 而合并为一个不可恢复动作；题型不要求经过 Chaoxing 题库链。默认单任务串行即可，多线程不是产品要求。两本调试书的只读限制不得成为发布限制。

#### UAI

复用 upstream 的完成进度与时长链路；账号内串行。必做章节必须完成；不影响完成度的口语文件、未知类型等可忽略并记录；影响完成度的 talk/讨论等必须按 upstream 能力执行。题目只在平台确实要求答案时进入统一答案链。

#### Cidaren

登录只保留 WebUI 的二维码/链接复制回传流程。`answer_lib` 作为低可信度历史来源导入全局题库，不得单独作为高可信答案。账号、课程、题库扫描、任务执行、失败重试和串行延时均需有状态与日志；限时题按保守频率执行。

### 2.4 题库、答案与题型语义

题库是当前部署环境全局共享的缓存，不按账号私有隔离。保存完整题目语义：题干、材料、图片、附件、共享上下文、选项文本及选项图片；不得依赖题号、平台 option id 或当前选项顺序。选项匹配使用规范化内容，保留顺序无关的集合/映射语义；图片先用 URL/hash，无法稳定时再用内容摘要或模型辅助。

必须覆盖：文本+图片混编、同一题干内混编、同一选项内混编、下划线样式挖空、空格挖空、共享材料、连线、共用选项、复合题、排序和 Provider-native 题型。规范化不能丢失原始渲染信息。

答案优先级：Provider Native/平台返回标答（若有）→ 全局 Local Cache → 限时题的 Instant 模型 → 非限时题配置模型 → 必要时国内灾备；manual 不是答案来源，而是提交前确认与补漏。外部题库暂不实现；Cidaren `answer_lib` 仅作为低可信历史导入。所有 AI 答案都缓存；平台事后返回正确结果时更新为已验证证据。缓存状态至少区分：未验证、单次验证、重复一致、存在冲突、已人工确认。出现对/错混合时不得一棒子判死，应进入模型仲裁或人工确认；单次“判对”不足以覆盖有冲突的记录。

不限时默认组合使用 GPT Router；请求失败/超时/不可用才走国内灾备。GPT-only 是管理员可选的高质量组合：不限时 Sol xhigh，限时 Luna；国内灾备分别绑定到组合中。每个模型配置 provider、endpoint、model、reasoning level、图像/文件能力、超时、重试、成本和适用任务类型。

### 2.5 调度、执行、通知与计费

- 手动执行和自动巡检分开；巡检默认关闭，可由用户/管理员按课程配置。
- 静默全量扫描仅限 Chaoxing，所有登录成功账号后台排队；失败自动重试并接续，验证码/网络阻断只延后当前账号，不阻断全局。管理员后台可查看扫描状态、阶段、失败原因、重试次数并手动重试。
- 执行请求必须冻结 owner、actor、账号、课程/任务和配置快照，避免中途换绑。
- 限时题使用保守延时与明确阈值；接近截止时 Instant 超时按策略降级/押答，但到人工确认截止仍绝不提交。
- QQ 只在群内 `@` 通知确认/补漏，不做私聊；WebUI 对需确认的独立作业/考试强制进入确认页。
- 余额归 owner；管理员代执行不扣管理员余额。计费支持固定价格和动态价格（模型实际用量、内置题库用量、加价比例/固定值），管理员维护凭据、价格和充值联系方式。

### 2.6 WebUI 与 Yunzai

逐页检查登录、密码设置/修改、Provider Account、重新认证、课程、任务、章节目录、题目审核、答案候选、执行、日志、扫描状态、用户/余额/模型/价格/通知设置。每个页面都要验证普通用户、operator、master 以及代用户 target owner 的读写边界。

Yunzai 插件使用统一注册入口：`#星芒状态`、账号、课程、任务、扫描、执行等命令保持群内工作；`e.isMaster` 只影响服务端确认的操作身份，不改变资源 owner。首次 QQ 注册后给 WebUI 一次性链接，用户设置密码后即可正常 Web 登录。

## 3. Windows 一键安装向导规格

### 3.1 目标与明确排除项

安装向导只负责本机依赖、Asterism、Worker、数据库、Yunzai 插件、配置、服务注册和健康检查；不创建或配置 Apache/Caddy/Nginx 等反向代理，不申请公网证书，不修改现有反代配置。安装结束输出本地监听地址和需要用户自行映射的反代信息。

### 3.2 向导输入

采用 PowerShell 图形/交互双模式，支持参数文件和无人值守模式。至少询问：

- 安装根目录、数据目录、日志目录、现有仓库/分支或本地源码路径。
- API/WebUI 监听地址和端口（默认仅 loopback）、公开 Web URL。
- Yunzai 根目录、Bot 实例/适配器、允许群、通知群、服务 Token。
- 启用的 Provider、各 Worker Python 路径/虚拟环境、浏览器可执行文件路径。
- 本地密钥生成、数据库路径、管理员初始账号/联系方式。
- AI 组合、endpoint、model、reasoning level、超时/重试和费用规则；密钥只写本机受 ACL 保护的 secret 文件或 Windows Credential Manager。
- 调度默认值、扫描并发、延时、视频倍速和通知策略。

### 3.3 依赖检测与安装

检测 Windows 版本/架构、PowerShell、Git、Rust/Cargo、Node.js/npm、Python/py launcher、pip/venv、Edge/Chrome/Chromium 及必要运行库。缺失依赖时优先使用 winget 或已批准的官方安装包；网络失败时给出可重试和离线安装路径，绝不静默下载未知二进制。记录版本、来源、校验值和安装日志。

自动创建四个 Worker 的 Python venv，安装各自 requirements；构建 Rust workspace 与 WebUI；准备浏览器运行时；执行数据库迁移。路径含空格、中文和非系统盘必须支持。

### 3.4 配置、服务与回滚

- 生成本地配置和密钥，写入前备份已有文件；重复运行必须幂等。
- 注册 Asterism API、Worker、调度器和可选 Yunzai 相关进程为 Windows 服务或任务计划；服务账户使用最小文件权限。
- 将插件复制/链接到指定 Yunzai 目录并写入 API URL、Web URL、Service Token、群配置；不覆盖用户已有插件配置。
- 启动前运行迁移、端口占用、权限、数据库读写、Worker health、WebUI 静态资源和 Yunzai 配置检查。
- 任一步失败保留诊断包并支持回滚到安装前备份；卸载默认只移除服务和安装器生成文件，不删除用户数据库/题库/日志，除非用户显式确认。

### 3.5 Windows 验收矩阵

在干净 Windows Server 与 Windows 10/11 上分别验证：依赖全无、部分依赖已有、已有 Yunzai、路径含空格/中文、无浏览器、端口冲突、网络中断、重复安装、升级迁移、服务重启、系统重启自动恢复、QQ 插件加载、Web 登录/改密、四 Provider 只读 health/courses/tasks、Chaoxing 扫描队列和失败接续。反代不作为安装器验收项。

## 4. 实施顺序与检查点

1. 完成本文档所列全仓审计，逐路由/服务/Worker 建立证据表，先修 owner/actor 和 QQ master 信任边界（代码审计与自动化边界已完成，现场仍待验收）。
2. 收口四 Provider 的只读与扫描状态，再补 Chaoxing 任务执行、题型、验证码、挑战模式和确认/截止语义。
3. 收口全局题库规范化、混编/挖空/共享材料和缓存信任状态。
4. 收口调度、并发、重试、通知、计费和管理员代用户流程。
5. 逐页验证 WebUI 与 Yunzai 命令，更新 `docs/0.0.1/README.md`、`DEPLOYMENT.md` 和运行手册。
6. 实现 Windows 安装向导，按本节验收矩阵在 Windows 上跑通；当前已加入 Windows Actions 的干净路径/中文空格路径安装烟测；每个检查点提交 Conventional Commit，并保留迁移/回滚记录。

## 5. 完成定义

只有同时满足以下条件，才可宣称 0.0.1 达到实际部署程度：

- 审计矩阵每项都有“已实现”或明确、可复现的现场阻断记录；不存在“管理员能创建但不能继续操作”的半闭环。
- QQ 普通用户注册、首次设密、Web 登录和 Yunzai `e.isMaster` master 操作链路可验证。
- 四个平台的已审计能力均有代码/fixture/现场验证之一，失败不会阻断其他账号；必须确认的任务在截止前未确认绝不提交。
- 全局题库不会因随机选项、图片/附件、混编或下划线挖空而错误复用；冲突答案可追踪并进入仲裁/确认。
- Windows 向导能在目标系统检测/安装依赖、配置、迁移、启动、健康检查、升级和回滚；反代仍由部署者自行配置。
