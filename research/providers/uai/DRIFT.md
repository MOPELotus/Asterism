# UAI drift register

| Risk | Static evidence | Required response |
|---|---|---|
| Login result/code shape changes | Current donors use string code `0`; captcha uses `1506` | Parse typed bounded envelopes; classify challenges as `HumanRequired` and never log bodies |
| JWT header format changes | Donors pass the returned JWT directly as `Authorization` | Validate through user-info/Course reads; do not guess a Bearer prefix |
| Login/user-info routes redirect or return HTML | Shared client does not follow redirects and both routes are audited JSON APIs | Classify redirects/404 as protocol drift and reject missing/non-JSON Content-Type before parsing |
| Read responses omit or change their success envelope | Audited UAI management APIs require numeric code `1` plus `success=true`; ucontent tree/progress/content require numeric code `0` | Require each route's exact success markers before consuming nested data; never accept a merely well-shaped body |
| JWT/openid are stored or renewed separately | Both values are required by different authenticated routes | Persist one strict ProviderCompositeSession and replace it atomically |
| Core rejects a native Password candidate before Provider validation | Password input uses a transient `ProviderSpecific` bundle but successful validation persists a `Composite` session | Declare `ProviderSpecific`, `Composite` and `Jwt` in Provider metadata; keep the candidate and replacement kinds distinct and require both to pass Core's metadata gate |
| Imported/native session metadata is confused | All paths store the same encrypted document with different lifecycle authority | Bind ManualImport, CaptureTool and BrowserExtension to Jwt and NativeProviderLogin to Composite; reject every other pairing and never renew imported sessions |
| Concurrent renewals overwrite a fresher session | Password credentials and composite session form one lifecycle set | Serialize by account, validate the new JWT, then compare-and-replace all three credentials atomically |
| JWT expiry is ignored or trusted as authentication | UAI supplies a JWT but user-info remains the native validation authority | Decode standard `exp` only as an early lifecycle/cache bound; never derive identity or validity from unsigned local claims |
| Expired JWT metadata prevents Password renewal | Core persists the same native-session expiry on the complete renewable credential set | Permit expired native Composite metadata only inside the exact username/password/composite renewal path, then user-info validate and atomically replace it |
| Unverified UAI becomes active accidentally | Native boundaries exist but have not passed live validation | Keep daemon registration disabled by default, require an independent explicit opt-in plus SecretStore and emit a Development warning |
| Course list and detail disagree on instance fields | List has `instanceId`; detail has `courseInstanceId` | Use stable CourseResource ID and refresh/bind detail before tree reads |
| Course tree outer envelope changes | Current response stores JSON text in `course` | Bound both layers and fail closed on non-string, malformed or oversized nested data |
| New tree role appears | Audited roles are Unit, Section, Node, Link and Group | Reject unknown roles and add a sanitized fixture before mapping them |
| Group ID disappears or becomes URL-only | Historical parser falls back to URLs for generic nodes | Require explicit bounded Group IDs; never persist route URLs as Task identity |
| Persisted Group facts become stale before a read | CourseResource detail supplies a fresh instance route and trees can change | TaskDetail re-lists CourseResources and rebuilds the exact Group; missing facts become RemoteChanged |
| Task-detail fingerprints change shape silently | Core requires versioned fingerprints for fresh detail validation | Prefix normalized Group hashes with `v1:` and bump the version when fingerprint material changes |
| Completion flags gain new values | Current donor requires `pass == pass2 == perm == 1` | Keep each flag independent and map only sanitized verified combinations |
| Progress strategy is missing, malformed or detached from the tree | Current Rust donor carries per-Group required/minimum-score/time-window/statistic facts in each per-Unit progress response | Fetch exactly one progress document for every fresh tree Unit, reject missing/extra Units or invalid field types/ranges, merge before fingerprinting and preserve donor defaults only when the complete strategy object is absent |
| Per-Unit progress belongs to another account or Course snapshot | Both backend donors show `open_id`, `tutorialId`, `unit_id` and `publish_version` beside the leaf map | Before exposing a native document, require exact session-openid, fresh Course-instance and Unit-route echoes; retain only a valid optional publish version and reject any disagreement with Course progress or the tree |
| Course progress and Course tree disagree on Unit set or publish version | Current Rust donor independently reads Course progress before Unit progress, takes Unit keys and the current submit publish version from that response, while the tree may also expose a version | Read both fresh documents, require exact top-level Unit-set equality, fill a missing tree version from Course progress, reject conflicting versions and fingerprint separate Course-Unit strategy facts before any Task is returned |
| A mutation runs outside the donor availability window | Current Rust progress exposes start/end epoch seconds and the MIT runner acts only under the strict nonzero `start < now < end` rule | Normalize either zero endpoint as unbounded, require positive ordered endpoints otherwise, then re-read exact Unit/Group progress and reject every ResourceExecution or SubmissionExecute outside the fresh window |
| Annotator token claims/signature change | Both backend donors independently use the same HS256 openid claims and millisecond expiry across content, progress and submission routes | Keep generation private to the native transport, pin an exact-time vector and fail closed on header/clock errors |
| Native submit unexpectedly depends on an SSO browser cookie or browser-only headers | The MIT donor submits through its login-populated cookie jar, the Apache donor keeps session cookies and JWT defaults, and the current Rust donor imports cookie, openid/CSRF, app/platform and optional `u-school`; none proves JWT-plus-annotator alone in a clean client | Capture one exact `ucontent` Cookie plus optional `u-school` from the same bounded request snapshot, retain school inside the composite rather than as an access token, inject both only into `ucontent`, keep submission at Development and validate native/fallback transports independently |
| Study-record duration unit/meaning drifts | Frozen MIT donor explicitly documents Course/Unit/Task `duration` in seconds | Keep the study-record route independent, bind exact CourseResource/Unit/Group identities and recheck with live before/after measurements |
| Course/Unit aggregate progress is collapsed into Task progress or accepted for another user | MIT donor exposes independent Course total and Unit finish-progress/duration/score/required facts keyed by CourseResource plus appUserId | Keep a separate bounded snapshot, bind fresh user-info and echoed appUserId, require unique `role=unit` IDs and finite `0..=100` progress/score; expose only through the dedicated shared capability once Core lands |
| Required-Course policy is confused with a progress leaf or fetched using stale strategy state | MIT donor refreshes Course detail, POSTs its strategy ID plus CourseResource and selects ordered per-Unit required Task IDs from the independent response | Keep a separate bounded policy owner, fresh-bind both request identities, require response Course/Unit strategy consistency, unique Unit/sort/Task IDs and typed score/unlock/time fields; reconcile with progress-leaf required only in the future shared policy contract |
| Progress duration is confused with study duration | Signed progress response also exposes an untyped numeric `duration` | Preserve progress value as raw only; populate seconds exclusively from the independent study-record response |
| Study-record tree duplicates or changes roles | Donor indexes nodeId and currently emits Unit/Section/Node/Link hierarchy | Require unique bounded node IDs, audited roles and one exact matching Task; reject drift before returning duration |
| Page residence stops producing duration | Current userscript relies on rendered page lifecycle, DOM/iframe clicks and optional media state | Prefer native network evidence when captured; otherwise use an account/Task-isolated rendered BrowserBridge plan and require fresh DurationRead after the residence budget |
| Browser DOM family changes | Frozen AutoPlayer `5.2.14` supports legacy `pc-slider`, Ant Tree/Menu and current `u3menu` plus two Tab families | Use a versioned allowlisted action plan, cap candidates/retries and fail with protocol drift when no uniquely bound visible leaf exists; never fall back to arbitrary page-wide clicks |
| Iframe message is accepted from the wrong page or session | Donor exchanges `UAI_CMD`, menu and click-result events with wildcard `postMessage` targets | Do not copy the wildcard trust model; require expected origin, frame/window, account/Task isolation key and per-session nonce on every command/result |
| Paused or video time is counted as ordinary residence | Donor stops its countdown while paused or while a current video is actively playing and restarts when the start index/budget changes | Persist a bounded residence cursor/budget in Core, make pause/restart explicit, cancel stale timers and verify only through a fresh exact DurationRead |
| Runtime settings change during execution | Master can override Provider defaults at account and Task scope | Core resolves one complete versioned snapshot before execution; native mutation and future BrowserBridge paths reject missing, unknown or stale-schema values and never reread mutable settings mid-attempt |
| Direct submit completes without duration | Backend donors submit answers independently of page residence | Keep CompletionService and DurationService separate; never claim execution from completion alone |
| Preset completion is forced through ordinary retrying TaskExecution | Current Rust and MIT donors mark study resources with a no-Question `submitType=2` POST, while `SubmissionDraft` requires at least one Question | Advertise ResourceExecution only with ExecutionVerify+ProgressRead, execute once, and let Core persist the attempt and recover through exact Group progress without replaying the POST |
| Preset labels select the wrong mutation shape | The Apache donor's active generic path inserts `instanceId=0` placeholders, while the current Rust donor uses the empty body only for fresh `tab_type=text|video` leaves | Treat the five base labels as candidates only; before any mutation refresh exact Unit/Group progress, require text/video inside the donor window, skip already-completed leaves and reject task/missing/unknown tab types |
| Encrypted content/answer framing changes | Donors currently use `unipus.` hex AES-ECB envelopes with a key suffix | Bound and validate every layer before decrypting; zeroize decrypted bytes on success and failure, recursively zeroize raw parsed string values, and never persist ciphertext, key material or route context |
| Nested Question content changes between encoded text and inline object | Current Rust donor explicitly accepts both representations | Apply one size bound and zeroizing parsed owner to either representation; reject all other nested types and bind the resulting semantic fingerprint before answer resolution |
| Group `base` cardinality no longer describes its Questions | Donors use either one homogeneous type or one type per Question | Require a bounded positive `question_num` plus exactly one supported type or an exact type-to-count cardinality before advertising or parsing Questions |
| Multi-Question module order or cardinality drifts | Current Rust and MIT donors serialize one ordered `quesDatas` row per native module and flatten child completion/judge rows in that same order | Require immutable draft positions `1..n`, exact fresh `question_num`/type cardinality, unique positive numeric module IDs and an exact ordered user-module readback before confirming any Question |
| Multi-Question client-authored metadata diverges | Current Rust donor uses minimal `contextVersion=1`/`answerVersion=1`; MIT/Apache multi builders use `1/0` plus locally fabricated course-answer score maps, while the MIT single builder uses minimal `0/0` | Retain the proven minimal `0/0` single body, use the current donor's minimal `1/1` multi body, never fabricate score/courseAnswer state, and keep both Development until separately authorized mutation validation |
| Course publish version is dropped, stale or hard-coded in judge metadata | Current Rust donor reads Course progress `publish_version` and emits it as `thirdPartyJudges[].versions.course` with `answer=3`; the MIT compatibility builder independently emits `course=0`/`answer=0` | Obtain a bounded positive numeric or numeric-string version from fresh Course progress, cross-check any tree copy and select the complete current pair at execution; use the independently evidenced legacy pair only for an explicitly injected transport without Course progress, include the version in the Task fingerprint and reject invalid or changed shapes before mutation |
| Question judge labels are guessed from Group `base` | Current Rust donor copies each decrypted content child/module `type` and child `replyType`; those labels can differ from the tree base | Preserve only bounded sanitized judge labels during answer-free parsing, require an exact label per answer child before every mutation, and fail before POST when content lacks that current contract |
| Missing or non-native Question ID reaches a mutation | Standard-answer and both donors' submission protocols use the positive numeric answer-entry instance ID | Require an explicit bounded remote Question ID for reads and a positive numeric instance ID for execution; never submit a Group/position fallback |
| A Question snapshot is reused against another Group route | Native Question IDs and option labels are not sufficient to prove the CourseResource/Unit/Group target | Persist the stable remote Task identity in sanitized Question metadata and require an exact match before answer resolution or draft construction |
| Answer submission targets a stale, completed or non-task progress leaf | The answer route mutates one Unit/Group while current progress separately identifies task mode, completion and scheduling | Pass the immutable Unit identity into transport, refresh Course detail plus exact Unit progress immediately before POST, require an incomplete `tab_type=task` Group inside its window and fail before body construction on mismatch |
| Submission throttling is mistaken for success | Donor returns `600001`/`600002` for rate limiting | Return typed retry state and never repeat a mutation without Core idempotency/recovery authority |
| An ambiguous mutation failure is retried inside the Provider | A timeout or body failure cannot prove whether the server accepted the request | Return the first Network error after one mutation attempt so Core enters receipt-independent verify-only recovery and never resubmits |
| Submit version cannot safely identify one user-module path | Submit acknowledgement supplies the version later combined with Group identity | Accept only a bounded ASCII path-component version before persisting the receipt; verification reuses the same validator |
| Submit receipt is accepted as result verification | Fresh user-module and progress reads are separate donor calls | Keep SubmissionExecute and SubmissionVerify separate and require a fresh identity-bound readback |
| A missing receipt causes verification to guess the current module version | The readback route is keyed by the submit response version | Return Inconclusive without transport I/O when no accepted version receipt exists |
| User-module route and response identify different Courses or Groups | The route uses fresh `courseInstanceId` while response and state carry separate module/submit metadata | Bind fresh Course detail, top-level and submit-info Course, exact Group-version module, submit-info Group and both version fields before inspecting answers |
| User-module answer is stale, partial or changed | `quesData` embeds separately encoded context and answer children | Require the complete exact ordered Question set, submitted context for every row, every child `isDone`, and exact immutable draft-answer equality |
| UAI task kinds acquire the wrong generic mutation default | Donors branch across choice, text, fillblank/banked-cloze, ordering, matching, oral, discussion, upload, preset and composite behaviors | Use exact typed mappings and content-derived judge metadata; implement oral/discussion/upload/exit-ticket as dedicated families, and fail closed only on structural drift rather than using unknown types as an exclusion policy |
| Matching or ordering answers are flattened | `basic-scoop-content` and `sequence` retain ordered child semantics in content and answer documents | Bind matching-left text and ordering child cardinality in the immutable Question snapshot, then reconstruct the exact ordered answer children inside execution |
| A multi-child choice module is flattened into one option set | The current Rust donor solves and submits every module child independently, and child option labels commonly repeat | Represent the module as one Composite Question, bind each child kind/options and rebuild one answer child per component without merging repeated labels |
| `video-popup` is treated as a fixed type or an empty preset | MIT reads its standard-answer children and submits type 2; the current Rust donor derives behavior from decrypted module/child `replyType` | Advertise from the exact tree base, derive only audited choice/text shapes from fresh content, keep the non-empty answer/judge rows, select type 2 only for an all-`video-popup` plan and fail closed on incompatible child semantics |
| Discussion reply receipt is mistaken for Group completion, or a reply page is accepted for the wrong topic | Donor performs topic lookup/reply mutation and a separate Group completion mutation | Bind every reply page to its requested topic, freeze the zeroizing exact reply intent, require exact current-user/content readback before authorizing one fresh Task/progress-bound Group completion, and keep final progress verification separate; shared Core must durably bind both attempts and never replay either ambiguous mutation |
| Upload paths or bytes escape Provider ownership, a compound upload is split, or an upload receipt is treated as completion | Donor obtains a short-lived token/fileKey before object-store upload; a single upload submits `instanceId=0`, while mixed upload and choice answers share one Group mutation | Keep bytes/token/key in zeroizing Provider owners, bind Task fingerprint/Course/Unit/Group/module/artifact across both remote stages, fresh-rebind before final POST, reject upload-only execution for a compound Group, require receipt-versioned exact key readback, and still use fresh progress as the completion authority; Core supplies the durable Artifact/Draft/attempt contract |
| Media routes disappear at the Question cache boundary or are rebound to another Task/Question | Donors can transcribe answer media, while Domain intentionally excludes fetch URLs | Encode media routes only in the encrypted QuestionSession continuation; bind its digest to Task/Group/Question/position/content fingerprint and the exact ordered attachment set, then recompute canonical URL, kind and attachment ID on decode before any future downloader can receive the route |

## Live-validation gate

After WebUI and Asterism-Plugin/Yunzai are complete and read-only test accounts
are available, before advancing verification:

1. validate Password login, captcha classification, JWT/annotator acceptance,
   expiry and recovery;
2. compare CourseResource and Unit/Section/Micro/Group trees with the visible
   account;
3. record per-Group flags plus Course/Unit completion and duration before and
   after ordinary study;
4. Capture the actual heartbeat/telemetry lifecycle and validate the rendered
   BrowserBridge page-residence/interaction path in the first batch;
5. verify native, BrowserBridge and Capture-dependent execution with independent
   fresh completion and duration reads;
6. commit only sanitized fixtures and a dated verification record.
